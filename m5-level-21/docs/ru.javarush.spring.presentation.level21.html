Уровень 21: Тестирование микросервисов

Мы построили распределенную систему, но как убедиться, что ее компоненты правильно взаимодействуют друг с другом? На этом уровне мы погрузимся в стратегии тестирования микросервисов. Вы узнаете, как адаптировать пирамиду тестирования для распределенных систем и почему контрактное тестирование с помощью Pact является ключевым для обеспечения совместимости между сервисами.

Мы вновь вернемся к Testcontainers и увидим, как с его помощью создавать надежные интеграционные и End-to-End тесты, которые проверяют сквозные бизнес-сценарии с реальными базами данных и брокерами сообщений. Наконец, мы разберемся, как тестировать асинхронные процессы с помощью библиотеки Awaitility.

Сложности тестирования

Тестирование микросервисов на порядок сложнее тестирования монолита. Мы сталкиваемся с проблемами распределенных систем:

  • Как протестировать Order Service, если для его работы нужен Product Service, который может быть недоступен в тестовом окружении?
  • Взаимодействие происходит по сети, которая может быть медленной или нестабильной.
  • Как подготовить тестовые данные, если они разбросаны по нескольким базам данных?
  • Как проверить результат операции, которая выполняется где-то в фоне после отправки события в Kafka?
  • Тест может упасть не из-за ошибки в коде, а из-за проблем с сетью, конфигурацией или недоступностью зависимостей.

Unit-тесты

Unit-тесты в микросервисах ничем не отличаются от Unit-тестов в монолите, и они по-прежнему составляют основу вашей стратегии тестирования.

  • Цель: проверить один класс в полной изоляции.
  • Инструменты: JUnit 5, Mockito.
  • Принцип: все зависимости (репозитории, клиенты к другим сервисам) мокируются.

Они быстрые, стабильные и составляют 70-80% всех ваших тестов. Они ничего не знают о том, что сервис работает в распределенной среде.

Интеграционные тесты (внутри сервиса)

Следующий уровень — проверка того, что все части одного микросервиса работают вместе как единое целое.

  • Цель: проверить взаимодействие от контроллера до базы данных.
  • Инструменты: @SpringBootTest, MockMvc (для REST), GraphQlTester (для GraphQL).
  • Принцип: запускается Spring Context для вашего сервиса. Внешние сервисы мокируются (например, с помощью @MockBean для Feign-клиентов). Зависимости вроде базы данных запускаются в Testcontainers.

Эти тесты гарантируют, что ваш сервис является внутренне согласованным и работает корректно.

Проблема взаимодействия

Order Service вызывает Product Service через Feign-клиент. В интеграционных тестах для Order Service мы мокируем этот клиент.

@SpringBootTest
class OrderServiceTest {
    @MockBean
    private ProductServiceClient productServiceClient;

    @Test
    void testOrderCreation() {
        when(productServiceClient.getProductById(1L))
            .thenReturn(new ProductDto(...)); // Мы "придумали" ответ
        // ...
    }
}

А что, если команда Product Service переименовала поле в ProductDto или изменила URL? Наши тесты для Order Service продолжат проходить (ведь они используют мок), но в продакшене все сломается!

Контрактное тестирование

Эту проблему решает Consumer-Driven Contract Testing (CDCT).

Вместо того чтобы "придумывать" ответы, сервис-потребитель (Consumer, Order Service) создает "контракт" — файл, в котором записаны его ожидания от API сервиса-поставщика (Provider, Product Service).

Этот контракт становится "законом" для поставщика. В CI/CD пайплайне поставщика запускается специальный тест, который проверяет: "Соответствует ли мое текущее API ожиданиям, записанным в контракте?". Если нет — сборка падает, и несовместимые изменения не попадут в продакшшен.

Фреймворк Pact

Pact — это самый популярный open-source фреймворк для реализации контрактного тестирования.

Он формализует процесс и предоставляет библиотеки для множества языков, включая Java.

Pact работает в два этапа:

  1. На стороне Consumer'а: пишете тест, который "проигрывает" взаимодействие с мок-сервером, предоставленным Pact. Если тест успешен, Pact генерирует файл контракта (.json).
  2. На стороне Provider'а: пишете тест, который "проигрывает" запросы из файла контракта против вашего реального, запущенного API, и сверяет ответы с теми, что записаны в контракте.

Интеграционные тесты с зависимостями

Микросервисы часто зависят не только от других сервисов, но и от инфраструктурных компонентов:

  • Базы данных.
  • Брокеры сообщений.
  • Кэши.

Использовать "боевые" или общие тестовые инстансы этих систем для автоматических тестов — плохая практика. Тесты становятся нестабильными и влияют друг на друга.

Решение — запускать временный, "чистый" экземпляр каждой зависимости для каждого тестового запуска.

Testcontainers

Мы уже встречались с Testcontainers при тестировании слоя данных. В мире микросервисов его роль становится еще более фундаментальной.

Testcontainers позволяет вам прямо в JUnit-тесте запустить любой сервис, который можно упаковать в Docker-контейнер.

Это означает, что ваши интеграционные тесты могут работать с:

  • Настоящей базой данных PostgreSQL, идентичной продакшену.
  • Настоящим брокером Kafka.
  • Настоящим кэшем Redis.

Это делает ваши тесты невероятно надежными, так как они выполняются в окружении, максимально приближенном к реальному, но при этом остаются полностью изолированными.

Пример тестирование с Kafka

Предположим, нам нужно протестировать, что наш NotificationService правильно отправляет событие в топик Kafka.

@SpringBootTest
@Testcontainers
class NotificationServiceTest {

    @Container
    private static final KafkaContainer kafka = new KafkaContainer(DockerImageName.parse("confluentinc/cp-kafka:7.0.1"));

    @DynamicPropertySource
    static void kafkaProperties(DynamicPropertyRegistry registry) {
        // Динамически передаем адрес временного Kafka-брокера в Spring
        registry.add("spring.kafka.bootstrap-servers", kafka::getBootstrapServers);
    }

    @Autowired
    private NotificationService notificationService;

    @Test
    void shouldSendNotificationEventToKafka() {
        // Act
        notificationService.sendWelcomeNotification("user123");

        // Assert
        // Здесь мы можем использовать тестовый Kafka-консьюмер,
        // чтобы "прослушать" топик и убедиться,
        // что наше сообщение действительно было отправлено.
    }
}

End-to-End (E2E) тесты

Это вершина пирамиды. E2E-тест проверяет сквозной бизнес-сценарий от начала до конца.

  • Цель: убедиться, что вся система в сборе работает как единое целое.
  • Принцип: запускается несколько микросервисов вместе с их зависимостями. Тест имитирует действия реального пользователя (например, через API Gateway) и проверяет конечный результат.

E2E-тесты дорогие, медленные и хрупкие. Их должно быть немного, и они должны покрывать только самые критически важные бизнес-потоки (например, "регистрация пользователя", "создание заказа").

Настройка E2E-тестов

Testcontainers снова приходит на помощь. С его помощью и Docker Compose можно описать и запустить всю вашу систему или ее часть.

  1. Создается docker-compose.yml, описывающий сервисы и их зависимости (product-service, order-service, PostgreSQL, Kafka).
  2. В JUnit-тесте используется @Testcontainers и DockerComposeContainer.
  3. Testcontainers запускает все контейнеры перед тестом.
  4. Тест выполняет API-вызовы к API Gateway или напрямую к сервисам и проверяет результат (например, что заказ появился в базе данных order-service).
  5. После теста Testcontainers останавливает и удаляет все контейнеры.

Тестирование асинхронных процессов

При тестировании EDA возникает проблема: как проверить результат, который появляется "когда-нибудь"?

@Test
void testAsyncProcessing() {
    // 1. Отправляем команду
    commandGateway.send(new CreateOrderCommand(...));

    // 2. Проверяем результат
    // Этот код выполнится мгновенно, а событие еще не успело обработаться!
    // Проверка почти наверняка упадет.
    assertThat(orderRepository.findById(...)).isPresent();
}

Awaitility — это небольшая, но очень мощная библиотека, которая решает эту проблему. Она позволяет писать тесты в стиле "подожди, пока...".

@Test
void testAsyncProcessingWithAwaitility() {
    // 1. Отправляем команду
    commandGateway.send(new CreateOrderCommand(...));

    // 2. Ждем до 5 секунд, пока условие не станет истинным
    await().atMost(5, TimeUnit.SECONDS).untilAsserted(() ->
        assertThat(orderRepository.findById(...)).isPresent()
    );
}
