Уровень 22: CI/CD и автоматизация развертывания

Мы написали отличный код и покрыли его тестами, но как доставить его на серверы быстро, надежно и без головной боли? На этом уровне мы изучим основы DevOps и автоматизируем процесс развертывания с помощью CI/CD.

Погрузимся в Docker, научимся "упаковывать" наши Spring Boot приложения в контейнеры, чтобы они работали одинаково в любом окружении. Наконец, мы создадим наш первый пайплайн с помощью GitLab CI, который будет автоматически собирать, тестировать и публиковать наше приложение при каждом изменении в коде.

Ручное развертывание

Представьте процесс "выкатки" новой версии без автоматизации:

  1. Разработчик собирает jar-файл на своей машине.
  2. Подключается к серверу по SSH.
  3. Вручную копирует файл.
  4. Останавливает старую версию приложения.
  5. Запускает новую.
  6. Молится, чтобы все заработало...

Этот процесс:

  • Занимает время, которое можно было потратить на разработку.
  • Легко допустить ошибку (скопировать не тот файл, забыть команду).
  • Что, если у вас 10 серверов? А 100?
  • Классическая фраза "а у меня на машине все работало" — следствие различий в окружениях.

Что такое CI/CD?

CI/CD — это практика, направленная на автоматизацию и ускорение процесса доставки программного обеспечения.

  • CI (Continuous Integration / Непрерывная Интеграция):

    • Разработчики часто (несколько раз в день) вливают свои изменения в общую ветку репозитория (например, main или develop).
    • Каждое такое вливание автоматически запускает сборку проекта и прогон автоматических тестов.
    • Быстро находить ошибки интеграции и получать обратную связь.

  • CD (Continuous Delivery / Непрерывная Доставка):

    • Логическое продолжение CI. Если сборка и тесты прошли успешно, артефакт (наш jar-файл или Docker-образ) автоматически готовится к релизу.
    • Артефакт публикуется в хранилище и может быть развернут на продакшен нажатием одной кнопки.
    • Continuous Deployment (Непрерывное развертывание) — еще более продвинутая версия, где успешная сборка автоматически развертывается на продакшен без ручного вмешательства.

Как это работает на практике?

Ты пишешь код, делаешь коммит, пушишь его на GitHub. GitHub Actions видит это событие (пуш) и запускает твой воркфлоу ... Если один тест падает, воркфлоу фейлится, и ты получаешь уведомление.

И вот тут самое интересное: можно настроить уведомления.

Например, если тесты не прошли, то GitHub Actions может отправить письмо тебе или всей команде, сообщив, что после коммита пользователя Username код не прошёл тесты. Это значит, что вся команда сразу увидит проблему. Иногда, на исправление могут дать время, и только потом вся команда получит письмо.

Контейнеризация

Проблема "на моей машине все работало" возникает из-за различий в окружениях: разные версии Java, разные системные библиотеки, разные настройки ОС.

Контейнеризация решает эту проблему. Она позволяет "упаковать" ваше приложение вместе со всем его окружением (Java, библиотеки, настройки) в единый, изолированный блок — контейнер.

Этот контейнер будет работать абсолютно одинаково на ноутбуке разработчика, на тестовом сервере и в продакшене в облаке. Контейнеры легковесны, быстро запускаются и обеспечивают изоляцию приложений друг от друга.

Dockerfile для Spring Boot

Создать Dockerfile для нашего Spring Boot приложения довольно просто. Мы будем использовать многоэтапную сборку (multi-stage build) — которая позволяет создать минимальный по размеру и более безопасный финальный образ.

Dockerfile

# --- Этап 1: Сборка (Builder) ---
# Используем образ с Maven и нужной версией Java для сборки проекта
FROM maven:3.8.5-openjdk-17 AS builder

# Копируем исходный код в контейнер
WORKDIR /app
COPY . .

# Собираем проект с помощью Maven. Тесты запускаются здесь!
RUN mvn clean package -DskipTests

# --- Этап 2: Запуск (Runner) ---
# Используем минимальный базовый образ только с Java, без Maven
FROM openjdk:17-jdk-slim

# Копируем только jar-файл из этапа сборки
WORKDIR /app
COPY --from=builder /app/target/*.jar app.jar

# Указываем порт, который будет слушать приложение
EXPOSE 8080

# Команда для запуска приложения при старте контейнера
ENTRYPOINT ["java", "-jar", "app.jar"]

Сборка Docker-образа

Имея Dockerfile в корне проекта, мы можем собрать образ и запустить контейнер.

1. Сборка образа

# Команда собирает образ на основе Dockerfile в текущей директории (-t задает имя и тег)
docker build -t my-app:1.0 .

2. Просмотр образов

docker images

3. Запуск контейнера

# Команда запускает контейнер из образа.
# -d: запуск в фоновом режиме
# -p 8080:8080: проброс порта 8080 из контейнера на порт 8080 хост-машины
docker run -d -p 8080:8080 my-app:1.0

Теперь ваше Spring Boot приложение работает внутри изолированного Docker-контейнера!

GitLab CI

GitLab CI/CD — это мощный инструмент для CI/CD, встроенный прямо в GitLab. Он использует специальный файл .gitlab-ci.yml, который должен находиться в корне вашего репозитория.

Когда вы делаете git push в GitLab, специальный процесс — GitLab Runner — находит этот файл и выполняет инструкции, описанные в нем.

Пайплайн (Pipeline) — это набор этапов (stages), которые описывают ваш процесс CI/CD. Например, build -> test -> release. Задача (Job) — это конкретная команда, которая выполняется на определенном этапе.

Структура .gitlab-ci.yml

Файл YAML имеет простую структуру.

# Определение этапов. Они будут выполняться в этом порядке.
stages:
  - build
  - test
  - release

# Задача 'build_job', которая выполняется на этапе 'build'
build_job:
  stage: build
  # Команды, которые нужно выполнить
  script:
    - echo "Compiling the code..."
    - mvn compile

# Задача 'test_job', которая выполняется на этапе 'test'
test_job:
  stage: test
  script:
    - echo "Running tests..."
    - mvn test

Простой пайплайн (CI)

Давайте создадим пайплайн, который будет собирать наш Spring Boot проект и запускать тесты.

.gitlab-ci.yml:

stages:
  - build
  - test

# Используем готовый Docker-образ с Maven
default:
  image: maven:3.8.5-openjdk-17

build_app:
  stage: build
  script:
    - mvn clean package
  # Сохраняем собранный jar-файл для следующего этапа
  artifacts:
    paths:
      - target/*.jar

run_tests:
  stage: test
  script:
    # Здесь мы могли бы запустить более сложные тесты
    # Но для примера просто выводим сообщение
    - echo "Running integration tests on" $CI_COMMIT_REF_NAME "branch..."

Продвинутый пайплайн (CD)

Теперь добавим шаги для сборки и публикации Docker-образа.

.gitlab-ci.yml:

stages:
  - build
  - test
  - package # Новый этап
  - release # Новый этап

# ... этапы build и test остаются такими же ...

package_docker_image:
  stage: package
  image: docker:20.10.16 # Используем образ с Docker
  services:
    - docker:20.10.16-dind # Запускаем "Docker-in-Docker"
  script:
    # Входим в реестр контейнеров GitLab
    - docker login -u $CI_REGISTRY_USER -p $CI_REGISTRY_PASSWORD $CI_REGISTRY
    # Собираем образ
    - docker build -t $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA .

release_docker_image:
  stage: release
  # ... (аналогично package_docker_image)
  script:
    # Публикуем (push) образ в реестр
    - docker push $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA

$CI_... — это предопределенные переменные GitLab CI.

Deployment

Публикация образа в реестре — это еще не развертывание на сервере. Как доставить контейнер на продакшен?

Можно добавить еще один этап в пайплайн, deploy, который будет:

  1. Подключаться к вашему серверу по SSH.
  2. Выполнять команду docker pull, чтобы скачать новую версию образа.
  3. Останавливать старый контейнер и запускать новый.

Это самый простой подход. В более сложных системах используются:

  • Инструменты управления конфигурацией (Ansible, Chef) для автоматизации настройки серверов и развертывания.
  • Оркестраторы контейнеров (Kubernetes, Docker Swarm), которые берут на себя всю сложность управления жизненным циклом контейнеров, их масштабированием и отказоустойчивостью.

Работа с переменными окружения

Никогда не храните секреты (пароли, ключи API) в Dockerfile или .gitlab-ci.yml!

Для этого есть специальные механизмы:

  • В GitLab CI:

    • Перейдите в Settings -> CI/CD -> Variables в вашем проекте.
    • Создайте переменную, например, DB_PASSWORD.
    • Пометьте ее как "Protected" (будет доступна только в защищенных ветках) и "Masked" (не будет видна в логах).
    • Теперь вы можете использовать $DB_PASSWORD в script'ах вашего пайплайна.

  • В Docker:

    • При запуске контейнера передавайте секреты через переменные окружения.
    • docker run -e DB_PASSWORD=$DB_PASSWORD_FROM_ENV ...
    • Ваше Spring Boot приложение автоматически "подхватит" эту переменную, если в application.yml есть плейсхолдер: password: ${DB_PASSWORD}.

CI/CD для микросервисов

В микросервисной архитектуре каждый сервис имеет свой собственный, независимый CI/CD пайплайн.

Это ключевое преимущество. Команда, отвечающая за product-service:

  • Работает в своем репозитории.
  • Имеет свой .gitlab-ci.yml.
  • Может развертывать новую версию своего сервиса 10 раз в день.

При этом она не затрагивает и не зависит от пайплайнов order-service или user-service. Это позволяет командам работать автономно и быстро, что и является одной из главных целей микросервисной архитектуры.
