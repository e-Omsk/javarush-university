Уровень 23: Управление конфигурациями и секретами

Мы развернули наши микросервисы, но как управлять их настройками? Хранить конфигурацию в application.yml каждого сервиса и пересобирать их при каждом изменении — путь к хаосу.

На этом уровне мы изучим паттерн централизованной конфигурации. Вы познакомитесь со Spring Cloud Config, который позволяет управлять настройками всех ваших сервисов из одного Git-репозитория и обновлять их на лету. Затем мы решим еще более важную проблему: безопасное хранение секретов. Познакомитесь с HashiCorp Vault — золотым стандартом для управления секретными данными в современной IT-инфраструктуре.

Проблема конфигурации

По мере роста количества микросервисов, управление их конфигурациями становится кошмаром:

  • Общие свойства (например, адрес брокера Kafka) дублируются в десятках application.yml файлов.
  • Чтобы изменить один общий параметр, нужно внести изменения в N репозиториев, пересобрать и развернуть N сервисов.
  • Нет единого места, где можно было бы увидеть всю конфигурацию системы.
  • Разработчики часто по неосторожности коммитят секреты (пароли от баз данных, API-ключи) прямо в Git-репозиторий, делая их видимыми для всех, у кого есть доступ к коду.

Паттерн внешняя конфигураци

Решение этих проблем — вынести конфигурацию из кода приложений в отдельное, централизованное хранилище.

Паттерн External Configuration Store (Внешнее хранилище конфигурации):

  1. Создается специальный сервис конфигурации.
  2. Он читает конфигурационные файлы из надежного источника (например, Git-репозиторий, база данных).
  3. Все остальные микросервисы при старте обращаются к этому сервису, чтобы получить свою конфигурацию.

Это позволяет управлять настройками всей системы из одного места, не трогая код и не переразвертывая приложения.

Spring Cloud Config

Spring Cloud Config — это проект из экосистемы Spring, который реализует паттерн внешней конфигурации. Он очень прост в настройке и идеально интегрируется со Spring Boot.

Архитектура состоит из двух частей:

  • Config Server: отдельное Spring Boot приложение, которое предоставляет конфигурацию по REST API.
  • Config Client: эта логика встраивается в ваши микросервисы.

По умолчанию, Config Server использует Git-репозиторий в качестве источника правды для конфигурационных файлов.

Как работает Config Server

Config Server — это, по сути, мост между Git-репозиторием и вашими приложениями.

Как работает Config Client

Чтобы микросервис начал получать конфигурацию от сервера, ему нужно стать "клиентом".

Для этого используется специальный файл bootstrap.yml (или bootstrap.properties), который загружается до application.yml. В нем указывается, где найти Config Server.

  1. При старте микросервис сначала читает bootstrap.yml.
  2. Он находит адрес Config Server'а.
  3. Отправляет на него запрос, сообщая свое имя (spring.application.name) и активные профили.
  4. Config Server возвращает нужные свойства.
  5. Эти свойства из удаленного источника "подмешиваются" в конфигурацию приложения с наивысшим приоритетом. Они переопределяют любые значения, заданные в локальном application.yml.

Настройка Config Server

Создать Config Server очень просто:

  1. На start.spring.io выберите зависимость Config Server.
  2. Включите его в главном классе приложения: 
    @SpringBootApplication
@EnableConfigServer
public class ConfigServerApplication {
    // ...
}
  3. Укажите адрес Git-репозитория в application.yml Config Server'а: 
    server:
  port: 8888
spring:
  cloud:
    config:
      server:
        git:
          uri: https://github.com/your-org/config-repo.git
          # clone-on-start: true

Настройка Config Client

Превратить микросервис в клиента еще проще:

  1. Добавьте зависимость spring-cloud-starter-config в pom.xml.
  2. Создайте файл src/main/resources/bootstrap.yml: 
    spring:
  application:
    # Имя, по которому Config Server будет искать файл конфигурации
    name: order-service
  cloud:
    config:
      # Адрес Config Server'а
      uri: http://localhost:8888
    В Spring Boot 3+ можно использовать spring.config.import: "configserver:http://localhost:8888" в application.yml вместо bootstrap.yml.

Теперь при запуске order-service сам сходит на http://localhost:8888 и загрузит свою конфигурацию.

Динамическое обновление

Одна из самых мощных возможностей Spring Cloud Config — это обновление конфигурации без перезапуска сервисов.

  1. Вы вносите изменение в конфигурационный файл в Git и пушите его.
  2. Вы отправляете пустой POST-запрос на эндпоинт Actuator /actuator/refresh вашего микросервиса.
  3. Получив этот сигнал, сервис заново обращается к Config Server'у, загружает обновленную конфигурацию и пересоздает бины, помеченные специальной аннотацией @RefreshScope.

Это позволяет, например, изменить уровень логирования или значение какого-либо бизнес-параметра на лету. Для автоматизации этого процесса используется Spring Cloud Bus.

Проблема секретов

Spring Cloud Config отлично решает проблему управления конфигурацией, но он не решает проблему управления секретами.

Vault

HashiCorp Vault — это open-source инструмент, который стал стандартом индустрии для безопасного управления секретами.

Vault — это не просто хранилище. Он предоставляет целый набор функций:

  • Все данные внутри Vault шифруются.
  • *Vault может генерировать секреты (например, пароль к БД) "на лету" с коротким сроком жизни.
  • Гибкая система политик, определяющая, какое приложение и к каким секретам имеет доступ.
  • Vault ведет подробный лог всех операций: кто, когда и к какому секрету обращался.
  • Vault может автоматически менять пароли в системах.

Интеграция Vault со Spring Boot

Spring Cloud Vault позволяет приложениям легко и безопасно получать секреты из Vault.

Приложение никогда не хранит секреты у себя. Оно получает их в момент запуска и хранит только в памяти.

Настройка Vault

Vault можно легко запустить локально в режиме для разработки.

1. Запуск сервера:

# Запускает Vault в памяти, выводит токен доступа и ключ для "расшифровки"
vault server -dev

2. Запись секрета через CLI:

# Устанавливаем переменные окружения, выданные на шаге 1
export VAULT_ADDR='http://127.0.0.1:8200'
export VAULT_TOKEN='...'

# Записываем секрет по пути secret/order-service
vault kv put secret/order-service db.password="super-secret-password"

Теперь в Vault хранится пароль для нашего order-service.

Клиент для Vault

Чтобы наше приложение Spring Boot могло прочитать этот секрет:

  1. Добавьте зависимость spring-cloud-starter-vault-config в pom.xml.
  2. Настройте подключение в bootstrap.yml: 
    spring:
  application:
    name: order-service
  cloud:
    vault:
      uri: http://127.0.0.1:8200
      token: "..." # Токен, полученный от Vault (в проде используются более безопасные методы аутентификации)
  3. Используйте свойство в application.yml: 
    spring:
  datasource:
    password: ${db.password} # Spring автоматически подставит сюда значение из Vault

Vault + Spring Cloud Config

Эти два инструмента не заменяют, а дополняют друг друга. Они используются для разных типов данных.

  • Spring Cloud Config (через Git):

    • Хранит нечувствительную конфигурацию.
    • Примеры: server.port, logging.level.root, spring.jpa.show-sql, таймауты, URL'ы публичных сервисов.
    • Конфигурация версионируется, ее изменения проходят code review.

  • HashiCorp Vault:

    • Хранит только секреты.
    • Примеры: пароли от баз данных, ключи API, токены, сертификаты.
    • Доступ к секретам строго контролируется политиками и аудируется.

При старте приложение обращается к обоим источникам и собирает из них свою финальную конфигурацию.
