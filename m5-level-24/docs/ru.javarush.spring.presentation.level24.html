Уровень 24: API Gateway и Service Discovery

Наши микросервисы умеют работать с конфигурацией и секретами, но остается два последних вопроса: как они находят друг друга в динамичной облачной среде, и как внешние клиенты взаимодействуют с этой сложной системой? На этом финальном уровне мы изучим два критически важных паттерна: Service Discovery и API Gateway.

Вы познакомитесь с Netflix Eureka для создания "телефонной книги" ваших сервисов, которая позволит им общаться по логическим именам, а не по хрупким IP-адресам. Затем мы построим API-шлюз с помощью Spring Cloud Gateway, создав единую и безопасную точку входа для всех внешних клиентов. Это последний штрих, который превратит наш набор сервисов в полноценную, связную и надежную систему.

Как найти сервис?

В предыдущих лекциях мы использовали "захардкоженные" URL в конфигурации: product-service.url: http://localhost:8081

В реальной среде это абсолютно не работает. Почему?

  • В облаке или Docker-среде IP-адреса и порты присваиваются динамически и могут меняться при каждом перезапуске.
  • У вас может быть не один, а десять экземпляров product-service, и их количество может меняться в зависимости от нагрузки. Какой из десяти адресов прописывать в конфигурации?
  • Если один экземпляр сервиса "упадет", клиенты должны автоматически переключиться на работающий, не требуя ручного изменения конфигурации.

Нам нужен автоматический и динамический способ для сервисов находить друг друга.

Паттерн Service Discovery

Паттерн Service Discovery решает эту проблему.

Идея заключается в создании центрального компонента — Реестра сервисов (Service Registry). Это своего рода "телефонная книга" для микросервисов.

Процесс работает в три этапа:

  1. При старте каждый экземпляр микросервиса "звонит" в реестр и сообщает свое логическое имя, IP-адрес и порт.
  2. Когда Order Service хочет вызвать Product Service, он сначала спрашивает у реестра: "По каким адресам сейчас доступен product-service?".
  3. Когда сервис корректно завершает работу или перестает отвечать, реестр удаляет его из своего списка, чтобы на него больше не отправляли трафик.

На стороне сервера

Netflix Eureka

Eureka — это реализация паттерна Service Registry от компании Netflix, которая стала частью экосистемы Spring Cloud.

Архитектура Eureka состоит из двух частей:

  • Eureka Server - это и есть "телефонная книга". Отдельное Spring Boot приложение, которое хранит реестр всех доступных сервисов.
  • Eureka Client - логика, которая встраивается в каждый ваш микросервис. Она отвечает за регистрацию сервиса в Eureka Server и за получение от него актуального списка других сервисов.

Eureka спроектирована с упором на отказоустойчивость. Даже если Eureka Server временно недоступен, клиенты продолжат работать с последней полученной копией реестра из своего кэша.

Клиенты хранят полученный реестр в локальном кэше, чтобы не "дергать" Eureka Server при каждом вызове другого сервиса.

Настройка Eureka Server

Создать Eureka Server — это стандартная процедура для Spring Boot:

  1. На start.spring.io выберите зависимость Eureka Server.
  2. Включите его в главном классе приложения: 
    @SpringBootApplication
@EnableEurekaServer // <-- Главная аннотация
public class EurekaServerApplication {
    // ...
}
  3. Настройте application.yml: 
    server:
  port: 8761 # Стандартный порт для Eureka
eureka:
  client:
    # Сервер не должен регистрироваться сам в себе
    register-with-eureka: false
    fetch-registry: false

После запуска по адресу http://localhost:8761 будет доступен дашборд Eureka.

Настройка Eureka Client

Чтобы микросервис регистрировался в Eureka:

  1. Добавьте зависимость spring-cloud-starter-netflix-eureka-client в pom.xml.
  2. Включите обнаружение в главном классе: 
    @SpringBootApplication
@EnableDiscoveryClient // <-- Включает логику клиента
public class ProductServiceApplication {
    // ...
}
  3. Настройте application.yml сервиса: 
    spring:
  application:
    name: product-service # Это имя будет зарегистрировано в Eureka
eureka:
  client:
    service-url:
      # Указываем, где находится наш Eureka Server
      defaultZone: http://localhost:8761/eureka/

Проблема клиентский доступ

Отлично, наши внутренние сервисы теперь могут находить друг друга. Но возникает новый вопрос: Как внешний клиент должен взаимодействовать с нашей системой?

  • Заставлять фронтенд знать адреса всех 50 микросервисов? Это создаст сильную связанность и усложнит разработку.
  • Какой сервис будет отвечать за аутентификацию и безопасность? Каждый по-своему?
  • Что если несколько сервисов нужно вызвать для одной страницы? Фронтенд будет делать множество запросов.

Эта диаграмма сравнивает хаотичную архитектуру, где клиент напрямую обращается к множеству микросервисов, с упорядоченной архитектурой, где единая точка входа (API Gateway) упрощает взаимодействие и централизует сквозные задачи.

Паттерн API Gateway

Решение этих проблем — паттерн "API-шлюз" (API Gateway).

API Gateway — это сервис, который является единой точкой входа для всех внешних запросов. Он действует как обратный прокси (reverse proxy), принимая запросы от клиентов и маршрутизируя их к соответствующим внутренним микросервисам.

Клиент взаимодействует только со шлюзом и не знает о внутренней структуре системы.

Функции API Gateway

API Gateway — это не просто "тупой" прокси. Он берет на себя множество сквозных задач:

  • Routing главная задача. Направляет запрос GET /api/products/123 на нужный экземпляр product-service.
  • Проверяет JWT-токены, API-ключи. Внутренние сервисы могут "доверять" запросам, прошедшим через шлюз.
  • Если у product-service есть 5 экземпляров, шлюз распределит нагрузку между ними (Load Balancing).
  • Может принять один запрос от клиента, "сходить" в три внутренних сервиса, собрать ответы и вернуть клиенту один агрегированный ответ.
  • Защищает систему от слишком частых запросов от одного клиента (Rate Limiting).
  • Централизованно логирует все входящие запросы.

Spring Cloud Gateway

Spring Cloud Gateway — это проект для создания API-шлюзов на основе Spring.

Ключевые особенности:

  • Построен на Spring WebFlux, что делает его неблокирующим и отлично подходящим для обработки большого количества одновременных соединений.
  • Маршруты и фильтры легко настраиваются через application.yml.
  • Из коробки" умеет работать с Eureka для динамической маршрутизации.
  • Позволяет легко модифицировать запросы и ответы "на лету".

Как работает Spring Cloud Gateway

Обработка запроса в Gateway строится на трех понятиях:

  • Route основной строительный блок. Состоит из ID, URI назначения, набора предикатов и набора фильтров.
  • Predicate условие для сопоставления. Если запрос удовлетворяет предикату, то применяется данный маршрут.
  • Filter код, который может изменять входящий HTTP-запрос или исходящий HTTP-ответ.

Схема обработки запроса

graph TD A(HTTP Request) --> B{Iterate through Routes}; B -- Route 1 Matches --> C(Apply Route 1 Filters); C --> D(Proxy to Downstream Service 1); B -- Route 1 No Match --> E{Route 2 Matches?}; E -- Yes --> F(Apply Route 2 Filters); F --> G(Proxy to Downstream Service 2); E -- No Match, More Routes --> B; E -- No Match, No More Routes --> H(Return 404 Not Found); D -- HTTP Response from Service 1 --> I(Apply Reverse Filters); I --> J(HTTP Response to Client); G -- HTTP Response from Service 2 --> K(Apply Reverse Filters); K --> J;

Обработка запроса в Gateway включает следующие шаги: получение HTTP-запроса, последовательное сопоставление с настроенными маршрутами на основе предикатов. При нахождении подходящего маршрута активируется цепочка Gateway-фильтров, которая может изменять запрос и ответ. После применения фильтров запрос проксируется к целевому сервису. Если ни один маршрут не соответствует запросу, возвращается ответ 404.

Настройка маршрутизации

Настроить маршруты очень просто в application.yml самого Gateway-сервиса.

spring:
  cloud:
    gateway:
      routes:
        # Правило 1: все запросы, начинающиеся с /api/users/,
        # направить на user-service
        - id: user_service_route
          uri: http://localhost:8081 # Пока что "захардкожено"
          predicates:
            - Path=/api/users/**

        # Правило 2: все запросы, начинающиеся с /api/products/,
        # направить на product-service
        - id: product_service_route
          uri: http://localhost:8082
          predicates:
            - Path=/api/products/**

Предикат Path — один из многих. Есть предикаты для проверки HTTP-метода, заголовков, параметров запроса и т.д.

Интеграция с Eureka

Жестко прописывать URI, как в прошлом примере — плохая практика. Gateway должен использовать Service Discovery!

Для этого нужно:

  1. Сделать Gateway Eureka-клиентом (добавить зависимость и аннотацию).
  2. Использовать специальный префикс lb:// (load-balanced) в URI маршрута.
spring:
  cloud:
    gateway:
      discovery:
        locator:
          # Включаем интеграцию с Service Discovery
          enabled: true
      routes:
        - id: user_service_route
          # lb://<имя-сервиса-в-eureka>
          uri: lb://USER-SERVICE
          predicates:
            - Path=/api/users/**

        - id: product_service_route
          uri: lb://PRODUCT-SERVICE
          predicates:
            - Path=/api/products/**

Теперь Gateway будет запрашивать у Eureka актуальные адреса USER-SERVICE, а встроенный балансировщик нагрузки (Spring Cloud LoadBalancer) будет распределять запросы между доступными экземплярами.

Фильтры Gateway

Фильтры позволяют выполнять сквозную логику. Их можно применять глобально или к конкретным маршрутам.

Добавим заголовок X-Request-Source: api-gateway ко всем запросам, которые проходят через шлюз.

spring:
  cloud:
    gateway:
      # Глобальный фильтр, применяется ко всем маршрутам
      default-filters:
        - AddRequestHeader=X-Request-Source, api-gateway

      routes:
        - id: user_service_route
          uri: lb://USER-SERVICE
          predicates:
            - Path=/api/users/**
          filters:
            # Фильтр для конкретного маршрута: убирает первый сегмент пути
            # /api/users/1 -> /1
            - StripPrefix=1

Существует множество встроенных фильтров: для добавления/удаления заголовков, перезаписи путей, ограничения скорости (rate limiting), реализации Circuit Breaker и многого другого.
